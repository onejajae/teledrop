# ADR 0003 — 인증 경로 세 개를 합치지 않는다

- 상태: 채택
- 날짜: 2026-07-26

## 맥락

사용자가 한 명뿐인데 인증 경로가 셋이다.

| 경로 | 누가 | 권한 | 수명 |
|---|---|---|---|
| 세션 쿠키 | 소유자, 웹 UI | 전체 | 로그인 동안 |
| 업로드 티켓 | 게스트 / 낯선 PC의 소유자 | **write-only.** 아무것도 돌려받지 못한다 | 24h 백스톱 + **1회 소진** |
| API 키 | 소유자의 iOS 단축어 | 업로드 (**private 고정**) | 장기, 재사용 (환경변수) |

셋 다 결국 "이 서버에 파일을 넣을 수 있다"는 같은 능력을 준다. 그래서 합치자는 생각이 반드시 나온다 — 실제로 설계 중에 두 번 나왔다.

## 결정

**합치지 않는다.** 세 경로를 각각 유지하고, 경계를 여기 기록한다.

## 근거

**업로드 티켓 ↔ API 키**: 갈리는 축은 **수명과 소진**이다. 티켓은 1회 쓰면 죽고 24시간 뒤 사라진다. 단축어는 매번 사람이 티켓을 발급해줄 수 없으므로 이 수명과 근본적으로 맞지 않는다. 반대로 재사용 가능한 장기 키를 남에게 줄 수는 없다.

**업로드 티켓 ↔ 세션**: 티켓은 낯선 환경에 놓이는 것이 전제다. 세션과 같은 권한을 줄 수 없다.

**API 키 ↔ 세션**: API 키는 소유자 크리덴셜이지만 웹 UI 전체 권한이 필요하지 않다. 업로드 하나만 열어둔다.

## 응답이 다른 이유

같은 "업로드"인데 돌려주는 것이 다르다. 모순처럼 보이므로 명시한다.

- **업로드 티켓**은 공유 링크를 반환하지 **않는다.** 게스트가 링크를 받으면 내 서버가 무료 파일 호스팅이 된다 ([ADR 0001](0001-write-only-guest-upload.md))
- **API 키**는 링크를 반환한다. 소유자 본인의 크리덴셜이라 해가 없고, 비용도 0이다

**단, API 키가 돌려주는 링크의 용도는 "남에게 주기"가 아니라 "내가 나중에 찾아가기"다.** 단축어 업로드는 private 고정이므로 그 링크는 로그인해야 열린다. 이걸 적어두지 않으면 나중에 "링크를 주는데 왜 public이 아니지?"로 헷갈린다.

## 결과

- 인증 코드가 세 군데다. 각각 작지만 셋이다
- **하나를 고칠 때 나머지 둘의 권한 경계를 확인해야 한다.** 특히 "업로드 응답에 링크를 추가"하는 변경은 티켓 경로에 새면 안 된다
- 넷째 경로를 추가하고 싶어지면 먼저 이 표에 넣어보고, 기존 셋 중 하나로 표현되지 않는지 확인한다

## 검토했으나 버린 것

- **devel의 API 키 서브시스템** — 테이블 + 발급 UI + 폐기 흐름으로 파일 8개였다. 나만 쓰고 기기별 독립 폐기가 필요 없으므로 환경변수 하나면 충분하다. 폰을 잃어버리면 compose 파일을 고치고 재시작한다
- **"비밀값을 한 번만 보여주는" UI** — 잘못 만들기 쉬운 물건이고, 안 만들면 그 위험이 없다
- **API의 `public=true` 파라미터** — 공개는 되돌릴 수 없는 행위이므로, 폰의 공유 시트 한 번으로 일어나는 경로를 만들지 않는다. 공개는 파일을 눈으로 보면서 웹에서 정한다
- **업로드 티켓에 `mode: 받기|보내기` 플래그** — 하나로 합치면서 권한만 나누는 방식. 발급할 때마다 판단이 생기고 실수하면 서버가 열린다
