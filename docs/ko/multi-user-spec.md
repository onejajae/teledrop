# 다중 사용자 전환 스펙

이 문서는 teledrop을 현재의 단일 로그인 사용자 구조에서 다중 사용자 구조로 전환하기 위한 변경 스펙 초안이다.

본 문서는 즉시 구현을 전제로 하지 않으며, 구현 범위와 영향도를 미리 합의하기 위한 계획 문서로 사용한다.

## 1. 목표
* 여러 사용자가 같은 teledrop 인스턴스를 함께 사용한다.
* 각 사용자는 자신의 드롭만 생성, 조회, 수정, 삭제할 수 있다.
* 각 사용자는 자신의 API key만 생성, 조회, 폐기, 삭제할 수 있다.
* 모든 사용자는 동일한 권한 수준을 가진다.
* 관리자 전용 역할이나 별도 운영자 권한은 도입하지 않는다.
* 드롭 slug는 전체 시스템에서 계속 전역 유니크를 유지한다.

## 2. 비목표
이번 전환 범위에 아래 항목은 포함하지 않는다.

* 관리자 역할, RBAC, 권한 등급
* 사용자 간 드롭 공유
* 팀/조직/워크스페이스 개념
* 사용자별 slug namespace
* 공개 회원가입 정책의 고도화
* 비밀번호 재설정 메일, 2FA, 외부 OAuth 로그인
* 사용자 프로필, 닉네임, 아바타 등 부가 기능

## 3. 현재 상태 요약
현재 구조는 사실상 단일 관리 사용자 모델에 가깝다.

* 로그인 계정은 `WEB_USERNAME`, `WEB_PASSWORD` 환경 변수 한 쌍으로 정의된다.
* 세션과 API key에는 `username` 스냅샷만 저장된다.
* `drops` 테이블에는 소유자 정보가 없다.
* private 드롭 접근 제어는 "로그인했는가"를 기준으로 처리된다.
* 로그인 사용자는 사실상 모든 private 드롭의 관리 기능에 접근할 수 있다.

이 구조는 다중 사용자 환경에서 소유권 경계가 성립하지 않으므로, 인증 저장소와 리소스 소유권을 함께 재설계해야 한다.

## 4. 대상 사용자 모델

### 4.1 사용자
* 각 사용자는 고유한 계정을 가진다.
* 모든 사용자는 동일한 권한을 가진다.
* 사용자 식별의 기준 키는 `user_id`이다.
* `username`은 로그인과 표시 용도로 사용하며 고유해야 한다.

### 4.2 드롭
* 각 드롭은 정확히 한 명의 소유자를 가진다.
* 드롭의 소유자만 해당 드롭의 관리 기능에 접근할 수 있다.
* slug는 전역 유니크를 유지한다.

### 4.3 API key
* 각 API key는 정확히 한 명의 사용자에게 속한다.
* API key 인증 결과는 해당 사용자의 identity를 반환한다.
* 사용자는 자신의 API key만 관리할 수 있다.

## 5. 요구사항

### 5.1 사용자 계정
필수 요구사항은 다음과 같다.

* 사용자 정보를 저장하는 `users` 테이블을 도입한다.
* 최소 필드는 아래와 같다.
  * `id`
  * `username`
  * `password_hash`
  * `created_at`
  * `updated_at`
  * `disabled_at` 또는 동등한 비활성 상태 표현 필드
* `username`은 유니크해야 한다.
* 로그인 검증은 환경 변수가 아니라 DB의 사용자 레코드를 기준으로 수행한다.

선택 검토 항목:
* 사용자 생성 경로를 UI로 열지, 초기에는 migration/CLI/seed로만 만들지
* `username` 변경 허용 여부

### 5.2 인증
필수 요구사항은 다음과 같다.

* 세션 인증은 `username` 문자열이 아니라 사용자 레코드에 연결되어야 한다.
* 인증 성공 시 애플리케이션 전체에서 사용할 identity는 최소 아래 필드를 포함해야 한다.
  * `user_id`
  * `username`
* `AuthIdentity` 또는 동등 타입은 anonymous 상태를 표현할 수 있어야 한다.
* 비활성화된 사용자는 새 로그인 세션을 만들 수 없어야 한다.

권장 사항:
* 기존 `WEB_USERNAME`, `WEB_PASSWORD`는 제거하지 말고 초기 관리자 시드 또는 부트스트랩 용도로만 축소하는 방안을 우선 검토한다.

### 5.3 세션
필수 요구사항은 다음과 같다.

* `auth_sessions`는 `username` 스냅샷 대신 `user_id`를 저장해야 한다.
* 세션 검증 시 사용자 레코드 존재 여부와 비활성 상태를 함께 확인해야 한다.
* 세션 검증 결과는 사용자 identity를 반환해야 한다.

권장 사항:
* 디버그 편의를 위해 `username` 스냅샷을 보조 컬럼으로 유지할지는 별도 결정한다.
* 다만 권한 판단의 기준은 항상 `user_id`여야 한다.

### 5.4 API key
필수 요구사항은 다음과 같다.

* `auth_api_keys`는 `created_by_username` 단독 구조에서 사용자 소유 구조로 바뀌어야 한다.
* API key는 최소 `owner_user_id`를 저장해야 한다.
* 감사 추적용 `created_by_username` 스냅샷은 초기 구현에서 유지하지 않는다.
* API key 조회 목록은 현재 로그인한 사용자의 key만 보여야 한다.
* API key 폐기/삭제는 소유자만 가능해야 한다.
* API key 인증 결과는 소유 사용자 identity를 반환해야 한다.

### 5.5 드롭 소유권
필수 요구사항은 다음과 같다.

* `drops` 테이블에 `owner_user_id`를 추가한다.
* 모든 드롭은 생성 시 소유자를 가져야 한다.
* 드롭 목록은 현재 로그인한 사용자의 드롭만 반환해야 한다.
* 드롭 상세 관리 페이지는 소유자만 접근 가능해야 한다.
* 드롭 수정, 삭제, 공개/비공개 전환, 즐겨찾기, 비밀번호 설정/해제는 소유자만 수행할 수 있어야 한다.

### 5.6 드롭 접근 정책
드롭 접근 정책은 아래와 같이 정의한다.

* `public` 드롭:
  * 누구나 링크를 통해 메타 조회 및 다운로드 가능
  * 비밀번호가 설정되어 있다면 비로그인 사용자는 비밀번호 또는 grant가 필요
  * 소유자는 비밀번호 입력 없이 관리 가능
* `private` 드롭:
  * 소유자만 메타 조회, 다운로드, 관리 가능
  * 다른 로그인 사용자도 접근할 수 없어야 한다
  * 비소유자에게는 존재 여부 노출 정책을 별도 결정한다

초기 권장 정책:
* 비소유자 private 드롭 접근 시 `403` 또는 서비스 기존 규칙에 맞는 접근 거부 응답을 사용한다.
* 존재 은닉이 필요하면 이후 별도 결정한다.

### 5.7 slug 정책
slug 정책은 기존과 동일하게 유지한다.

* slug는 전체 시스템에서 전역 유니크다.
* 서로 다른 사용자가 동일 slug를 가질 수 없다.
* slug availability 검사도 전체 시스템 기준으로 동작한다.

이 결정은 구현을 단순하게 만들지만, 사용자 수가 늘어날수록 slug 충돌 빈도는 다소 증가할 수 있다.

### 5.8 웹 UI
필수 요구사항은 다음과 같다.

* 로그인 후 `/drops`는 내 드롭 목록만 보여야 한다.
* `/drops/{slug}` 관리 페이지는 소유자만 접근 가능해야 한다.
* `/settings/api-keys`는 내 API key만 보여야 한다.
* 업로드는 로그인 사용자 기준으로 소유자가 자동 지정되어야 한다.
* shared 페이지에서 public 드롭은 기존처럼 링크 접근이 가능해야 한다.
* shared 페이지에서 private 드롭은 비소유자에게 공개되지 않아야 한다.

### 5.9 REST API
필수 요구사항은 다음과 같다.

* `GET /api/auth/me`는 현재 사용자 identity를 반환해야 한다.
* `GET /api/drop`는 현재 인증된 사용자의 드롭만 반환해야 한다.
* `POST /api/drop`는 현재 인증된 사용자를 owner로 하여 드롭을 생성해야 한다.
* `PATCH /api/drop/{slug}`와 `DELETE /api/drop/{slug}`는 owner만 수행 가능해야 한다.
* `GET /api/drop/{slug}/meta` 및 `GET /api/drop/{slug}`는 public/private 정책에 따라 접근이 제한되어야 한다.

권장 사항:
* `GET /api/auth/me`는 단순 문자열 username보다 구조화된 JSON 응답으로 바꾸는 편이 이후 확장에 유리하다.

## 6. 데이터 모델 변경

### 6.1 신규 테이블
신규 `users` 테이블을 추가한다.

예상 컬럼:
* `id`
* `username`
* `password_hash`
* `created_at`
* `updated_at`
* `disabled_at`

### 6.2 기존 테이블 변경
`drops`
* `owner_user_id` 추가
* 필요 시 index 추가

`auth_sessions`
* `user_id` 추가
* 기존 `username`은 제거 또는 감사용 보조 필드로 축소

`auth_api_keys`
* `owner_user_id` 추가
* 기존 `created_by_username`은 제거

### 6.3 애플리케이션 타입 변경
아래 타입과 DTO가 영향을 받는다.

* `AuthIdentity`
* session DTO / record
* API key DTO / record
* drop DTO / entity
* drop repository query contract

## 7. 저장소 및 유스케이스 변경

### 7.1 인증 계층
다음 변경이 필요하다.

* 사용자 조회 repository 추가
* username 기반 로그인 검증 use case 추가 또는 기존 교체
* 세션 검증 결과를 username 문자열이 아닌 identity 또는 user record 기반으로 변경
* API key 검증 결과도 identity 기반으로 변경

### 7.2 드롭 계층
다음 변경이 필요하다.

* 드롭 생성 command/input에 owner 정보 포함
* 목록 조회에 owner scope 필터 추가
* 단건 조회 시 access policy에 owner 판정 추가
* 수정/삭제 시 owner 검증 추가
* 현재의 "로그인했으면 비밀번호 체크 bypass" 로직은 제거 또는 owner 판정으로 교체

### 7.3 API key 계층
다음 변경이 필요하다.

* 목록 조회에 owner 필터 추가
* revoke/delete에 owner 검증 추가
* 생성 시 owner 지정 추가
* verify 시 owner identity 반환 추가

## 8. 데이터베이스 전환 전략

### 8.1 기본 전략
이 전환은 `main`에서 DB breaking change를 허용한다.

권장 전략은 아래와 같다.

1. Alembic migration 체인을 제거한다.
2. 앱 시작 시 빈 데이터베이스에 현재 스키마를 자동 생성한다.
3. `users`가 비어 있으면 `WEB_USERNAME`, `WEB_PASSWORD`로 초기 사용자 1명을 생성한다.
4. 기존 Alembic/레거시 데이터베이스는 자동 변환하지 않고 명확한 오류로 중단한다.
5. 운영 문서에는 기존 `share/database.db` 백업 후 삭제/재생성을 안내한다.

### 8.2 이전 데이터 호환
이 전환에서는 이전 데이터 자동 호환을 지원하지 않는다.

* 기존 DB metadata는 새 스키마로 자동 backfill하지 않는다.
* `share/` 아래 기존 업로드 파일은 새 DB에 자동으로 다시 연결되지 않는다.
* 필요하면 운영자가 백업 DB를 별도로 보관하고 수동 복구 절차를 설계해야 한다.

### 8.3 실패 시 고려사항
* 초기 사용자 생성에 실패하면 앱 시작이 중단되어야 한다.
* `WEB_USERNAME` 중복이나 빈 값 처리 규칙을 명확히 해야 한다.
* 운영 환경에서 업그레이드 전 DB 백업을 권장한다.

## 9. 문서 및 설정 변경
문서와 설정 영향은 다음과 같다.

* 설치 문서에서 단일 `WEB_USERNAME`/`WEB_PASSWORD` 설명을 수정해야 한다.
* 인증/API 문서에서 사용자 기반 세션 및 API key 소유권을 설명해야 한다.
* 필요하면 초기 사용자 seed 전략을 운영 문서에 추가해야 한다.

설정 검토 항목:
* `WEB_USERNAME`, `WEB_PASSWORD`를 완전히 제거할지
* 아니면 최초 부트스트랩 전용 환경 변수로 유지할지

초기 구현 단계에서는 부트스트랩 전용으로 유지한다.

## 10. 테스트 요구사항
아래 시나리오는 최소한 자동화되어야 한다.

* 사용자 A와 B가 각각 로그인 가능
* 사용자 A가 만든 드롭은 A 목록에만 노출
* 사용자 B는 A의 private 드롭을 볼 수 없음
* 사용자 B는 A의 public 드롭을 링크로 볼 수 있음
* 사용자 B는 A의 드롭을 수정/삭제할 수 없음
* 사용자 A의 API key는 A만 목록/폐기/삭제 가능
* API key 인증 시 올바른 사용자 identity가 반환됨
* 기존 Alembic/레거시 DB는 명확한 오류로 거부됨

## 11. 구현 순서 제안
권장 구현 순서는 아래와 같다.

1. `users` 스키마 및 앱 시작 시 DB 초기화 추가
2. 사용자 repository / 로그인 use case 추가
3. session / API key를 `user_id` 기반으로 전환
4. `AuthIdentity` 확장
5. `drops.owner_user_id` 추가 및 drop repository 필터링 도입
6. drop policy 및 mutation 권한 수정
7. 웹/UI/API 응답 수정
8. 테스트 보강
9. 운영/설치 문서 갱신

## 12. 오픈 이슈
아래 항목은 구현 전 최종 결정이 필요하다.

* 초기 사용자 생성 경로를 UI/CLI로 확장할지
* `username` 변경 허용 여부
* 비활성 사용자 처리 방식
* private 드롭 비소유자 접근은 `404`로 마스킹한다

## 13. 수용 기준
이번 다중 사용자 전환은 아래 조건을 만족하면 완료로 본다.

* 두 명 이상의 사용자가 하나의 인스턴스에서 동시에 독립적으로 사용 가능
* 각 사용자는 자신의 드롭만 관리 가능
* 각 사용자는 자신의 API key만 관리 가능
* slug는 전역 유니크로 유지
* 관리자 없이 모든 사용자가 동일한 권한 모델로 동작
* 기존 Alembic/레거시 DB는 자동 변환 없이 명확한 오류로 거부
